3. IMPLEMENTED USER LOOP

New + Import P6 / Open work -> activity search and metadata -> native selection
-> Capture preview -> Add -> review/filter -> select native elements -> edit
individual relations -> auto-save -> close/reopen -> validate/export.

Activity search uses code/name/WBS. Review supports activity-only, captured-
element-only and free text including category, level, status, ID and note.
A row is a relationship, not an element or a comma-separated activity list.
Capture reports excluded objects and keeps an explicit buffer; Add re-resolves
its UniqueIds before committing. Revit selection changes alone do not alter it.

Initial categories: Walls, Floors, Structural Columns, Structural Framing.
Category-specific level parameters precede Element.LevelId fallback. Unknown
level is explicit; levels are not geometry-splitting or construction-zone rules.
Links, types, imports, containers, Parts, nested families and other categories
are visibly excluded. Group member instances are not automatically expanded.

4. MANY-TO-MANY SEMANTICS

Each relationship has a persistent relation ID, native element endpoint,
snapshot-qualified activity endpoint, whole-element scope, associated-work
meaning, note and timestamps. Within a working document, an identical endpoint
pair is unique. There is no exclusive activity ownership of an element.

- Add creates absent pairs; existing pairs and other activities stay untouched.
- Duplicate Add is a no-op, including no new persisted revision.
- Reassign changes the activity of selected relationship IDs only, retaining
  their notes/creation evidence. Same target is a no-op.
- A reassign that would duplicate another pair refuses the entire operation.
  It does not silently merge relations or discard notes. The user may explicitly
  remove the redundant old pair or choose another target.
- Remove deletes only selected pairs, never the native object or its other pairs.
- Edit note modifies selected pairs; no role/animation semantics are inferred.
- To correct an element endpoint, explicitly Add the new pair and Remove the old
  pair. Missing identities are never automatically substituted.
- Undo restores the preceding committed relationship state as a new revision.
  One undo step is available within the current session, not after reopening.

Multiple activities on one object are associations, not geometry partitions,
quantity allocations, percentages or a “last task wins” rendering policy.

5. IDENTITY, P6 NORMALIZATION AND VALIDATION

Working documents own a persistent logical model key. Native element identity
is model key + Revit UniqueId; diagnostic ElementId is text, never the resolver
for previous mappings. Exact lookup reports resolved/missing/ineligible; records
are retained when missing. ProjectInformation UniqueId is corroborating evidence,
not a globally unique lineage guarantee. Every Open asks for explicit same-model
confirmation; distinct native model evidence is refused. Copies can preserve IDs
and still require operator judgment; no automatic fork detection is promised.

The pilot requires a saved, unmodified, non-workshared native host. It does not
write parameters, geometry, Extensible Storage, view overrides or transactions.
Select in Revit changes only UI selection. Revit Undo is not external-file Undo.

P6 Professional V24.12 APIBusinessObjects is the qualified profile. Multiple
projects can be presented; exactly one is normalized into each working document.
The real supplied fixture retains 209 activities/72 WBS and Thai text. IDs remain
strings; activity keys include source SHA-256 + project ObjectId + activity
ObjectId. These are immutable snapshot keys, not cross-database migration keys.

Retains project/activity/WBS identifiers, GUIDs when present, WBS hierarchy,
source order, type/status/calendar reference, selected progress/duration metadata
and distinct current/planned/actual/remaining-early dates. Missing/nil/empty/value
remain distinct. ISO timestamps retain source precision/offsets; absent timezone
is not converted to UTC. Current dates are not a contractual baseline.
No CPM, calendar calculation, dependencies/resources/cost/UDF preservation or
full P6 XSD validation is claimed. Unsupported dialects/MSP are refused.

Input safeguards include a 20 MiB XML bound, DTD/entity declaration rejection,
project/WBS/duplicate checks, cycle detection and date validation. Working JSON
is bounded to 64 MiB, rejects duplicate fields/non-finite numbers and unknown
format versions, and validates keys, scope, references and endpoint uniqueness.

Schedule is stored inside the working document; the source XML path is not
needed to resume. Check source XML detects changed hashes without replacing
the snapshot. No refresh/migration UI is implemented.

6. PERSISTENCE, RECOVERY AND EXCHANGE

Working format: suzanoo-mapping-work-1 (.mapping.json), UTF-8 JSON.
External file is authoritative. Each confirmed edit validates a candidate,
checks expected disk checksum, stages a same-directory temporary file, flushes
and publishes a replacement, then updates in-memory state. Saved status is not
set before the commit boundary. Revision/history record operation and local
actor label; username is not authenticated identity.

IronPython/Windows uses an OS-held FileStream writer lock, Flush(true),
File.Replace with .bak, and non-overwriting File.Move for new files.
CPython tests use OS locking and same-filesystem publication/replacement.
A live lock or external file change refuses writes. OS locks release on process
exit; lock-marker presence alone is not treated as a stale active lock.

Target a local writable NTFS folder, one writer. Network/sync-folder concurrency,
locking across copied files and power-loss durability are NOT qualified.
A .bak contains one prior committed revision, not long-term archival history.
Recover backup validates it and writes a NEW file; the original is never replaced
by recovery. Corrupt/unsupported input is rejected without repair-in-place.

Save / Check verifies the committed file and rechecks native endpoints; edits
already auto-save, so there is no hidden unsaved project state to discard.
Close and canceled dialogs preserve prior work. Staged failures leave the prior
committed memory/file intact; tests inject failures before publication.

Exchange format: suzanoo-mapping-exchange-1-pilot (.exchange.json suggested).
This is a versioned pilot contract, not a frozen industry-wide schema. It contains
origin work/revision/model identity, current saved native revision evidence,
normalized schedule, referenced native elements, explicit relationship records
and validation results. Absolute RVT paths are omitted from exchange.

Export validates references/cardinality, requires exact native resolution and
writes a NEW filename. Missing/ineligible related elements block successful
export while remaining in work. Incomplete/mixed-awareness dates produce
relationship-valid output with time_ready=false; source-local complete dates
remain source-local, not timezone-certified. Geometry correspondence is explicitly
not evaluated. Export never changes working assignments.

Renderer adapters later own object-handle resolution, export-artifact crosswalks,
transforms, geometry decomposition and playback. No 4DBIM, renderer, mesh data,
IFC export or guessed IFC aliases are implemented in MS-1.
